# Foodiemo v2 開發流程

更新日期：2026-09-09

文件狀態：開發規劃，不代表功能、連線或驗收已完成。本文將使用者已確認的產品要求與後端實作提案分開；待確認事項不能自動轉成變更前端的授權。

## 1. 目標與不可偏離的原則

使用者已確認：前端介面與互動模式已定案。v2 的工作是**依照「前端原始程式碼/frontend」保留現有產品操作，將資料接至 PostgreSQL，讓後續推薦演算法能接入**。

- 新程式、測試、設定範例與開發文件放在 `v2開發/`。
- `前端原始程式碼/` 保留為唯讀參考；將前端複製至 v2 後，只做必要串接與原互動下的缺陷修正。
- `v1開發/frontend/` 的重設計探索頁不是 v2 的版型或互動基準。
- 保留原生 HTML／JavaScript、頁面結構、主要樣式、照片呈現、按鈕位置、手勢與返回路徑，不更換前端框架。
- 不新增搜尋欄、分類工具列、分頁按鈕、側欄，也不把手機式流程改成桌面資料列表。
- 不因資料庫有欄位，就自行增加評分表單、公開／私人開關、收藏按鈕或其他原版沒有的操作。
- 原版只有示意的功能，保留其視覺入口並列明串接狀態；不自行刪除入口，也不新增假的成功狀態。提示文案需要調整時列入差異清單。
- 既有程式 bug 不等於已定案的產品要求。修復「取消卻離開」「刪整篇只刪首圖」時，維持原本操作意圖。
- 任何會改變畫面、選項、手勢或操作步驟的提案，先提供具體差異與原因供使用者確認；一般資料映射、API 與後端實作依既定範圍執行。
- 不把規劃文件中的擴充功能當成原版已具備的互動，也不以測試通過代替需求符合度。

2026-09-09 已實作第一批原版複本與餐廳推薦串接，完成自動化與真實 PostgreSQL 驗證；其餘階段及手機實機尚未完成。實際狀態以 [本批紀錄](docs/test-report-2026-09-09.md) 為準。

## 2. 已盤點的原版互動基線

以下來自原始 HTML／JavaScript 的程式碼盤點；實際瀏覽器與手機手勢需在階段 0 建立操作證據。

| 區域 | 必須保留的使用者互動 | 現有資料／實作狀態 |
| --- | --- | --- |
| 主容器 index | 左：回憶日曆；中：拍照首頁；右：社群；預設首頁；左右滑動、回彈、指定 tab 返回 | 三個 iframe；生效的手勢在 index 內，不能誤以未載入的 main.js 為準 |
| 拍照首頁 home | 頭像→個人頁；右上圖示→通知；左下放大鏡→推薦；快門→拍照／相簿／取消；鉛筆→編輯 | 最新紀錄第一張照片；API 優先，部分 IndexedDB 備援；中央人物膠囊無事件 |
| 快門快速記錄 | 選照片後直接上傳，留在首頁更新照片，不先進編輯頁 | upload_memory_post，支援相簿多圖 |
| 餐廳推薦 search | 進頁取得 3 間；直向大圖卡；頂端下拉更新並替換整批；點卡開覆蓋詳情；地圖另開；返回首頁 | recommendations?count=3；沒有搜尋框、分類篩選、分頁；詳情使用卡片物件 |
| 偏好 onboarding | 六題二選一；選中樣式；確認後下一題；進度點；完成回首頁 | 飯／麵、葷／素、中／美式、清淡／重口味、餐廳／街頭、獨享／分享；只存 IndexedDB |
| 回憶 memories | 月份箭頭；日期照片縮圖與多張提示；點圖開限動；左右點擊；3 秒自動播放；下拉關閉；單圖刪除 | 從 get_memories 依日期與照片展開；切回頁面會回目前月份 |
| 照片編輯 edit | 大預覽、縮圖格、加圖、單選／多選、選取順序數字、Finish、依來源返回 | 新增／更新 API；caption 固定空；地點開關預設 Kaohsiung；標記只送 Tagged |
| 社群 social | 我的社群／饗你推薦；直向貼文、多圖橫滑、張數、愛心、留言、更多選單 | 我的社群讀 API；推薦貼文是內建示例；按讚只改記憶體；檢舉／共同編輯只有提示 |
| 留言 comments | 進獨立頁；固定底部輸入；非空白啟用 Post；Enter 送出；成功清空並更新；回社群 | get_post／add_comment；目前字串拼 HTML 需安全修正 |
| 帳號與 OTP | 註冊表單、密碼顯示切換、四位數字驗證、錯誤重試、登入、忘記密碼 | 原版已發 API 請求；Google 成功直接首頁，普通註冊驗證後進偏好 |
| 個人 profile | 點頭像換圖；名稱原地編輯且失焦儲存；Email；Subscription；登出確認；返回首頁 | 名稱／頭像／會員 API；其餘設定列多數沒有事件 |
| 付款 payment | 原卡片視覺、送出中狀態、成功／取消返回原來源 | 顯示卡片欄位，實際只呼叫升級 API，沒有真實金流 |
| 通知 message | 通知列表上下捲動、左上返回 | 靜態示例；不是聊天；沒有點通知開內容的事件 |
| 跨頁與 PWA | 紀錄／個資變更後同步；子操作避免誤切主頁；既有返回流程 | BroadcastChannel、postMessage、localStorage、IndexedDB、Service Worker |

### 2.1 明確不是現成能力的項目

- 原版沒有餐廳收藏入口、三項評分輸入、公開／私人切換、完整貼文文字編輯、朋友選擇器或餐廳選擇器。
- 原版社群推薦的是**貼文**；放大鏡頁推薦的是**餐廳**，兩者不能混用同一資料契約。
- 原版看起來像餐廳評論的詳情區塊，實際是資料來源說明，不能自行換成評論列表。
- 原版的數字選取順序不是拖曳排序。
- 通知、共同編輯、檢舉與無事件設定列不是已完成後端功能。

## 3. 架構與目錄

```text
v2開發/
├── frontend/              # 原版複本；保留 UI，只改必要串接
│   └── api/               # 共用請求、資料映射、錯誤與身分處理
├── backend/app/
│   ├── api/               # 與原前端相容的 HTTP 入口
│   ├── services/          # 帳號、偏好、紀錄、推薦、會員
│   ├── repositories/     # PostgreSQL 存取
│   ├── models/
│   ├── schemas/
│   ├── recommendation/   # 可替換推薦提供者
│   └── core/             # 設定、驗證、連線、儲存
├── migrations/            # 延續既有資料庫版本歷史
├── tests/                 # 邏輯、PostgreSQL、API、UI、手勢
├── scripts/               # 啟動、核對、備份及安全測試入口
├── docs/                  # 互動基線、契約、差異與驗收紀錄
├── .env.example
├── v2開發流程.md
└── v2測試流程.md
```

此為預定結構，依實作需要逐步建立，不宣稱目前已有這些腳本。

資料流為「原版 UI → 共用 API／相容映射 → FastAPI → PostgreSQL」。推薦提供者放在後端，前端不持有 DB、SSH 或演算法服務憑證。

優先保留原前端所需的 JSON 形狀與操作觸發點；可以保留原 API 路徑，也可以用集中式映射轉接。先建立 API 契約表，再選擇一致做法，不在每一頁散落特例。不得因沿用原請求帶 email，就讓 email 決定操作身分。

## 4. 資料與環境策略

- 目標為既有 PostgreSQL `project_db`。v1 曾核對 9.5.25，並建立 `0001_baseline`；v2 開工須重新唯讀核對版本、Schema、版本表與權限，不能只信舊報告。
- 可重用已核對的 v1 後端基礎、安全經驗及精確 Schema，但不能直接複製整個 v1 當成 v2 完成品。
- 不遷移 DEMO SQLite 的真實帳號、貼文或留言；如需匯入，另列範圍。
- 結構變更前產生新的完整備份，於新隔離 DB 驗證還原。舊備份不能無條件代表本次變更已受保護。
- v2 使用獨立 `foodiemo_v2_test`、專用測試角色及 `v2開發/test-uploads/`；不可與 project_db、備份還原庫或 v1 測試資料混用。
- 延續同一 Alembic 版本歷史：先核對已套用基線，新變更接在其後；不另建互相衝突的版本表，不對既有庫重跑建表基線。
- 缺少 DB 設定明確失敗，不退回 SQLite、內建餐廳或其他資料庫。
- 本機設定、憑證、上傳、備份與含資料的測試證據不進 Git。實際帳密不寫進本文件。
- 後端是身分、所有權與會員的依據。本機儲存可保留偏好草稿與必要快取，但不能冒充保存成功或通過權限驗證。
- 四位 OTP 視覺保留；後端需處理有效期、嘗試次數、發送限制、單次使用與重設 Token，外部寄信設定另驗。

### 4.1 按功能核對資料映射

| 原版需求 | 現有資料來源／待補部分 |
| --- | --- |
| 登入、名稱、Email、生日、電話 | users；頭像、驗證與重設資料依實際 Schema 補 migration |
| 六題偏好 | 現有 14 張表沒有明確專用模型；提案增加版本化的使用者偏好儲存，保留每題 key/value |
| 三間餐廳與詳情 | restaurant_rows、business_hours；照片、評分與價位缺可靠來源，不造值 |
| 首頁／日曆／我的社群 | records、photos；同一筆紀錄使用一致 ID、日期與照片順序 |
| 留言 | platform_comments；軟刪除、作者與目標可見性 |
| 模擬會員 | memberships、payment_transactions；狀態由後端判斷 |
| 推薦執行與事件 | recommendation_runs、recommendation_items、user_restaurant_events |
| 朋友標記、共同編輯等示意 | 不把 Tagged 當真實使用者 ID；完整功能另行確認 |

照片缺值可保留原位置的佔位呈現，但不能把通用示意圖宣稱為店家實拍。含大寫的 googleMaps_id、reviewsCount、categoryName 必須正確對應。reviews_rows.created_at 不能當原始評論時間。

## 5. 分階段開發

### 階段 0：原版基線、環境與資料保護

1. 檢查 Git 與 v2 目錄；複製原版 frontend 及所需靜態素材，排除真實設定、DB、上傳與機密。
2. 在隔離瀏覽器來源建立原版畫面、操作路線及必要錄影／截圖；API 尚不可用時可用明示測試 fixture，不能冒稱真實串接。
3. 建立頁面／按鈕／手勢／返回路徑清單，記錄哪些是實際互動、示意或缺陷。
4. 列出「允許串接改動」與「待確認 UI 差異」。未經確認的視覺或流程差異不得混入後續實作。
5. 核對 project_db、migration 狀態、權限與工具相容性；完成本次備份、隔離還原、v2 測試庫及照片目錄。
6. 建立 v2 獨立啟動位置與測試來源；不佔用其他正在使用的埠，不混用 v1／原版 Service Worker。

驗收：原版互動有可對照證據，資料保護與測試防呆可執行；此時還不宣稱所有功能已接好。

### 階段 1：相容串接骨架與原版餐廳推薦

1. 建立設定、連線、驗證入口、錯誤格式與前端共用請求模組。
2. 保留 search 頁原卡片、進頁取 3 間、頂端下拉替換、覆蓋詳情、地圖與返回操作。
3. PostgreSQL 餐廳映射為原版 title／subtitle／img／rating／hours／price／address／mapLink 等欄位；加上穩定餐廳 ID。
4. 提供清楚標示版本的基礎推薦提供者，先以可重現的候選篩選與抽取／輪替完成流程，不宣稱個人化。
5. 下拉是新一批推薦請求，不是追加列表或跳下一頁；候選充足時可輪替，不足時不湊重複店家或假資料。
6. 修正 source 對應文案，避免 PostgreSQL 真資料仍被原判斷顯示為 Google Places 或內建備援。
7. 缺值、空資料、逾時與重試沿用原畫面位置呈現；不新增永久搜尋／分頁控制。
8. 主容器若尚需登入，使用隔離測試身分驗證串接，不在正式環境加假登入繞過。

驗收：原版推薦操作不變，真實餐廳與 ID 可核對；資料少於 3 間、下拉連點及晚回應皆正確。

### 階段 2：帳號、個人資料與六題偏好

1. 串接原版註冊→OTP→六題偏好→首頁，以及登入、登出、忘記密碼與重設流程。
2. 保留原表單、四格 OTP、失焦存名稱與頭像選取操作；後端完成安全驗證，不相信前端 email／旗標。
3. 六題偏好在完成時送後端保存；後續登入可讀回，不能只存 IndexedDB。
4. 保存偏好版本與選項 key/value，讓推薦模組可透過後端取得；儲存失敗時保留可重試內容，不假裝完成。
5. Google 登入沿用現有入口；未配置時列明限制。是否讓新 Google 使用者也進問答，屬流程變更，先確認，不自行增加。
6. 檢查切換帳號、頭像、舊快取與過期登入，避免顯示前一帳號資料。

驗收：原版帳號與個資操作接到 DB，六題偏好可在另一個登入工作階段由後端讀回。

### 階段 3：照片紀錄、首頁、日曆與我的社群

1. 保留快門選完直接上傳，以及鉛筆進入編輯後 Finish 的兩條獨立流程。
2. 同一筆 records／photos 驅動首頁第一張照片、月曆縮圖、限動與我的社群。
3. 保留單選／多選及數字順序；正確保存新舊照片的整體順序，不能因非同步壓縮改變順序。
4. 保留目前地點／標記按鈕的狀態；釐清固定地點與 Tagged 示意的資料語意，不偽造真實餐廳或朋友關聯。
5. 單張刪除只刪該圖，整篇刪除處理全部關聯；檔案失敗與 DB 失敗有補償策略。
6. 修正取消捨棄仍返回、空紀錄保留舊月曆、訊息格式不一致等缺陷。
7. 保留 3 秒限動、左右點擊、跨日期播放、下拉關閉、回到目前月份與外層滑動鎖定。
8. 以明確 Asia/Taipei 規則輸出日期；不改月曆操作。
9. 原版沒有公私控制。上線前需確認新紀錄可見性規則；不新增開關、不默認擴大既有內容公開範圍。

驗收：兩條新增流程、編輯、單圖刪除、整篇刪除後，三個主畫面與重新整理資料一致；上傳、所有權及照片存取正確。

### 階段 4：留言與社群資料串接

1. 串接原版留言頁，保留 Post／Enter、提交後更新與返回社群。
2. 使用安全文字渲染，提交中防止重複送出，錯誤可在原頁恢復。
3. 保留「我的社群／饗你推薦」、多圖橫滑、張數與更多選單。
4. 「饗你推薦」從示例轉真實公開紀錄前，確認內容範圍與可見性；不與餐廳推薦混用。
5. 按讚、檢舉、共同編輯、通知與無事件設定列仍按原版狀態列入待辦；是否本批實作另行確認，不以提示當成後端功能。

驗收：留言保存、權限與安全文字通過；社群流程及手勢維持基線。未串接入口有明確狀態清單。

### 階段 5：推薦演算法接入與事件

1. 與演算法團隊確認版本化契約，提供人工範例與替換實作測試。
2. 輸入由後端提供已驗證使用者、count（原 UI 為 3）、偏好版本與必要條件；不提供密碼或 Token。
3. 輸出為餐廳 ID、排名、可選分數／原因；後端檢查有效性，補齊原 UI 欄位。
4. 回傳可附 run_id、algorithm_version 等追蹤欄位，但不把實作細節加成新的操作控制。
5. 保存 runs／items，定義卡片實際曝光、點擊詳情、下拉重取與地圖點擊的事件語意；事件須可去重並驗證來源關聯。
6. 原 UI 沒有收藏，不為了蒐集收藏事件增設按鈕。
7. 慢回應、重複下拉與模組失敗不覆蓋較新的結果；備援若使用必須能辨識。
8. 替換推薦提供者時，前端操作與公開欄位契約維持；新資料需求仍需契約版本協調。

驗收：基礎提供者與另一個受控實作都能跑過同一套 UI／API 測試；偏好、run、items、事件與使用者關聯正確。推薦品質與模型研究另行驗收。

### 階段 6：模擬會員與交接

1. 沿用個人／社群進會員頁、送出中、成功／取消回來源的路徑。
2. 本案沿用模擬付款方向，不串真實金流；原版卡片欄位如何呈現測試內容及模擬提示，先列出具體差異確認，不收集真實卡資料。
