# Foodiemo v1 測試流程

更新日期：2026-09-08  
文件性質：測試計畫，尚未代表以下測試已執行或通過。  
對應計畫：[v1開發流程](v1開發流程.md)。

## 1. 測試目的

確認 DEMO 前端改接 PostgreSQL 後，資料讀寫、身分權限、照片與日曆、推薦介面及模擬會員流程能正確運作。測試隨開發階段執行，不等所有功能完成才開始。

目前確認的只有 DBeaver 連線成功及資料表清單可見；尚未確認後端連線、migration、v1 API 或端到端流程。

## 2. 環境與資料隔離

| 環境 | 允許用途 | 限制 |
| --- | --- | --- |
| `project_db` | 唯讀核對；完成備份與驗證後的正式整合 | 不執行自動化清表、故障注入或批次測試資料建立 |
| 獨立 PostgreSQL 測試資料庫 | migration、API／整合測試、測試資料建立及清理 | 使用明確測試名稱與測試帳號，與正式資料庫分離 |
| 瀏覽器測試設定 | 操作測試帳號及獨立 API 環境 | 避免與正式登入、localStorage、IndexedDB、Service Worker 快取混用 |
| 獨立照片測試目錄／儲存空間 | 上傳、刪除及失敗補償測試 | 不可指向正式上傳位置 |

- 整合測試使用 PostgreSQL，不以 SQLite 代替驗證型別、外鍵、JSONB 或交易行為。
- 測試入口在任何寫入或清理前核對目標資料庫名稱、主機／連接埠及測試標記；若目標為 `project_db` 或未明確指定測試環境，直接拒絕執行。
- 測試資料庫清理只能作用於已核對的隔離目標，不能依模糊名稱或路徑刪除。
- 不把正式個資、密碼雜湊、Token、完整連線字串放進測試報告、截圖或 Git。
- 資料庫版本目前為 9.5.25；先核對驅動、備份工具及 migration SQL 相容性。若日後升級，於新版本重跑整合測試。

## 3. 每次測試的執行順序

1. 記錄 Git commit／工作版本、測試日期、資料庫版本、migration 版本及測試範圍。
2. 確認 VPN、SSH Tunnel、後端與測試資料庫狀態，檢查環境設定沒有指向正式資料庫。
3. 準備最小測試資料，固定可重現的時間與資料內容。
4. 執行受本次變更影響的邏輯測試。
5. 執行 PostgreSQL 整合及 API 測試。
6. 若影響使用者操作，執行對應瀏覽器流程，包括重新整理與錯誤情境。
7. 記錄結果；失敗先定位並修正，再重跑失敗案例及相鄰流程。
8. 清理該批測試資料與照片；保留不含敏感內容的驗收證據。

具體安裝、啟動及測試命令會在選定並建立工具後補入 README。此時不提供尚不存在的腳本或宣稱可執行的命令。

## 4. 測試資料設計

- 使用者 A、B：彼此不同帳號；另備未登入及過期登入情境。
- 餐廳：至少包含完整資料、缺少可選欄位、含特殊字元名稱及非連續 ID。
- 紀錄：A 的公開／私人紀錄、B 的紀錄、單圖／多圖、無餐廳關聯的紀錄。
- 留言：一般文字、換行、HTML 特殊字元、已軟刪除留言。
- 照片：合法小圖、多張不同順序圖片、過大檔案、偽裝圖片及失效檔案。
- 會員：未開通、有效、剛到期及重送同一模擬付款請求。
- 推薦：有結果、無結果、無效餐廳 ID、重複餐廳、重複排名及推薦模組失敗。

測試使用固定小資料集，不依賴正式餐廳／評論總筆數；不可因正式資料成長導致測試失敗。

## 5. 分階段測試案例

### A. 環境、備份與 migration

| 編號 | 情境 | 預期結果 |
| --- | --- | --- |
| ENV-01 | 後端唯讀連線 | 可讀資料庫版本與 Schema，沒有隱藏寫入 |
| ENV-02 | 缺少或錯誤資料庫設定 | 明確失敗，不建立或改用 SQLite |
| ENV-03 | VPN／Tunnel 中斷 | API 在設定的逾時內回應可辨識錯誤，畫面不無限等待 |
| ENV-04 | 執行資料庫備份及隔離還原 | 命令成功，還原後 Schema、關鍵筆數與關聯可核對；備份檔沒有進 Git |
| ENV-05 | 對既有 Schema 建立基線 | 不重建或覆蓋現有資料表與資料 |
| ENV-06 | 在空測試資料庫執行 migration | 可完整建立 v1 所需結構，重新執行不重複套用 |
| ENV-07 | 在隔離環境驗證變更回復 | 可依 downgrade 或備份還原策略回復；有資料損失可能的變更須記錄限制 |
| ENV-08 | 測試入口誤設為 `project_db` | 寫入／清理前停止執行 |

### B. 餐廳查詢

| 編號 | 情境 | 預期結果 |
| --- | --- | --- |
| REST-01 | 列表、分頁、條件篩選 | 回傳符合條件的資料與穩定排序，參數超限被拒絕或依契約限制 |
| REST-02 | 有效與不存在的餐廳 ID | 有效資料正確；不存在時明確回應，不依 ID 是否連續推算 |
| REST-03 | 缺照片、地址、評分或營業時間 | 前端合理顯示缺值，不呈現 undefined 或假資料 |
| REST-04 | 特殊字元及含大寫的資料庫欄位 | 查詢與顯示正確，文字不當作 HTML 執行 |
| REST-05 | 空結果、API 錯誤及無法連線 | 無資料與載入失敗是不同畫面狀態 |
| REST-06 | 評論時間及評分 | 不將匯入時間當原始評論時間，不將不存在的欄位當 Google 評分 |

### C. 帳號與權限

| 編號 | 情境 | 預期結果 |
| --- | --- | --- |
| AUTH-01 | 註冊、重複 Email、非法欄位 | 正常建立；重複與非法輸入不產生多餘帳號 |
| AUTH-02 | 正確／錯誤密碼登入與登出 | 身分狀態正確，API 不回傳密碼雜湊等敏感欄位 |
| AUTH-03 | Cookie 過期但 localStorage 有 Email | 前端要求重新登入，不跳回無法使用的首頁 |
| AUTH-04 | 未登入呼叫需驗證 API | 回應未登入，不以請求 email 代替驗證 |
| AUTH-05 | A 嘗試編輯／刪除 B 的內容 | 拒絕且 B 的資料保持不變 |
| AUTH-06 | 修改 localStorage 會員或帳號欄位 | 後端權限不改變 |
| AUTH-07 | 切換帳號、登出再登入 | 不顯示前一帳號的私人快取及頭像 |
| AUTH-08 | 驗證碼／重設 Token 錯誤、過期、重用 | 依設計拒絕，不能只提供 Email 就重設密碼 |

Email 與 Google 登入：自動化測試使用受控替身；實際外部登入／寄信需有設定後另行驗證，不能以替身測試宣稱外部串接成功。Cookie 驗證採用時，另測部署設定下的跨來源與跨站請求保護。

### D. 收藏、紀錄、照片與日曆

| 編號 | 情境 | 預期結果 |
| --- | --- | --- |
| REC-01 | 收藏、重複收藏、取消收藏 | 關聯唯一，重送不建立重複資料 |
| REC-02 | 建立文字、評分、地點與餐廳關聯 | 欄位保存正確，無效關聯與超出範圍評分遭拒 |
| REC-03 | 多圖建立、重新排序、保留舊圖加新圖 | 重新查詢及整理頁面後順序一致 |
| REC-04 | 刪除其中一張照片 | 只移除該照片，其他照片與紀錄仍在 |
| REC-05 | 刪除整篇多圖紀錄 | 所有相關資料依規則處理，重新整理不再出現殘留貼文 |
| REC-06 | 編輯中按返回，再按取消捨棄 | 留在編輯頁，內容仍在 |
| REC-07 | 刪除最後一篇，另一頁刷新日曆 | 舊照片清空，顯示真正空狀態 |
| REC-08 | 跨午夜與月份邊界的紀錄 | 依 Asia/Taipei 日期顯示於正確日曆格 |
| REC-09 | 非圖片、偽裝圖片、超大檔案 | 後端拒絕，畫面顯示原因，不留下錯誤紀錄 |
| REC-10 | 部分照片儲存失敗或 DB commit 失敗 | 資料與檔案依補償策略保持一致，不刪掉尚未成功替換的舊圖 |
| REC-11 | A 直接取得 B 的私人紀錄／照片 URL | 存取遭拒，不能只靠隱藏列表達成隱私 |

公開改私人後也需測試先前可用的存取方式；照片儲存策略必須能符合所宣告的隱私行為。

### E. 社群與留言

| 編號 | 情境 | 預期結果 |
| --- | --- | --- |
| SOC-01 | 公開探索與個人清單 | 公開探索不包含私人紀錄，個人清單僅包含自己的資料 |
| SOC-02 | 新增留言與重新整理 | 留言保存且作者由後端驗證身分決定 |
| SOC-03 | 對私人、不存在或已刪除紀錄留言 | 不建立非法或孤立留言 |
| SOC-04 | 留言包含 `<b>文字</b>` 或事件處理屬性 | 畫面視為文字，不建立可執行 HTML；僅在隔離環境使用安全測試字串 |
| SOC-05 | 留言軟刪除 | 一般查詢不顯示已刪除內容，重整後狀態一致 |
| SOC-06 | 快速重複按提交 | 避免同一次操作意外建立多筆留言，提交期間狀態清楚 |

### F. 推薦契約與互動事件

| 編號 | 情境 | 預期結果 |
| --- | --- | --- |
| RECO-01 | 基礎推薦有結果 | 餐廳存在，排名及 API 欄位符合契約，版本明確 |
| RECO-02 | 推薦為空或演算法不可用 | 依契約回應空結果、明示備援或錯誤，不假裝成功產生個人化推薦 |
| RECO-03 | 模組回傳重複餐廳、排名或無效 ID | 驗證拒絕或依明確規則處理，不寫入違反約束資料 |
| RECO-04 | 保存推薦 runs／items | 使用者、版本、條件、排名及餐廳對應正確，部分失敗不留半套結果 |
| RECO-05 | 曝光、點擊與收藏 | 依事件定義產生，帶正確餐廳及可選推薦關聯；必要時去重 |
| RECO-06 | A 提供 B 的推薦執行 ID | 不可將事件歸到 B 的推薦紀錄 |
| RECO-07 | 替換測試推薦實作 | 前端與公開 API 契約測試維持通過 |

推薦準確率、模型訓練效果與離線排名指標由演算法研究另行制定；本階段只驗證接入契約與資料流程，不以介面測試代替推薦品質評估。

### G. 模擬付款與會員

| 編號 | 情境 | 預期結果 |
| --- | --- | --- |
| PAY-01 | 開啟模擬付款頁 | 清楚顯示不扣款，不收集卡號或 CVV |
| PAY-02 | 未登入開通或指定其他人 Email | 未登入拒絕，不能為其他帳號開通 |
| PAY-03 | 正常完成一次模擬付款 | 保存模擬交易，會員有效 30 天，重新登入仍正確 |
| PAY-04 | 連點、相同請求重送、網路回應遺失後重試 | 同一次交易不重複開通、不重複延長 |
| PAY-05 | 交易寫入或會員更新失敗 | 兩者保持一致，不出現只有成功交易或只有開通會員 |
| PAY-06 | 有效會員再次購買 | 依 v1 預設規則拒絕再次購買，不累加天數 |
| PAY-07 | 到期前、到期時及到期後 | 後端時間判斷一致；到期後可重新開通 |
| PAY-08 | 修改前端會員旗標 | 後端會員狀態不被改變 |

模擬交易測試不代表真實金流驗證完成；本計畫不測真實扣款、退款或第三方回呼。

## 6. 瀏覽器整合驗收路線

使用測試環境及測試帳號，至少手動跑過：

1. 註冊／登入 → 探索餐廳 → 詳情 → 收藏 → 重新整理確認。
2. 選餐廳 → 建立多圖餐飲紀錄 → 日曆與個人頁查看 → 編輯 → 單圖刪除 → 整篇刪除。
3. A 建立公開與私人紀錄 → B 查看社群與直接詳情 → 對公開紀錄留言。
4. 取得基礎推薦 → 點擊餐廳 → 收藏 → 核對推薦與事件關聯。
5. 模擬付款 → 會員狀態更新 → 重新登入 → 受控時間下驗證到期。
6. 登入過期、API 失敗、空資料與重複點擊時，畫面可恢復且沒有假成功。

檢查桌面與窄螢幕的導覽、表單、照片及日曆。iframe 側滑、相簿橫滑與頁面上下捲動需確認不互相誤觸；手機觸控操作應至少在一台實機驗證，若只有模擬裝置須註明。啟用 Service Worker 時，測試更新後資源一致性及登出後私人資料不殘留。

## 7. 通過標準與阻擋條件

- 每階段對應案例通過後，才將該階段標記完成；未實作案例標記「未執行／待實作」，不能填通過。
- 資料遺失、跨帳號存取、私人照片外洩、腳本注入、誤連正式庫寫入、會員開通不一致，均為阻擋交付問題。
- API 通過不等於畫面驗收通過；語法檢查不等於執行測試。
- 外部寄信、Google 登入、部署網路或實機尚未驗證時，報告列明，不以推測宣稱通過。
- 不以不穩定的外部推薦／地圖 API 作為核心自動化測試依賴。
- 通過相關測試後不無目的重跑全部測試；只有新變更、失敗或未解疑慮才擴大範圍。里程碑交付執行核心流程回歸。
