# Foodiemo v1 開發流程

更新日期：2026-09-08  
文件性質：開發計畫；列出的功能、環境與驗收項目不代表已完成。

## 1. 目標與已確認決策

v1 的工作是把既有 PostgreSQL 與 DEMO 前端整合成可用、可測試的系統，整理架構並預留個人化推薦演算法的接入位置。演算法研究可與本計畫平行進行。

- 新程式、測試、設定範例及開發文件集中在 `v1開發/`。
- `前端原始程式碼/` 保留作為 DEMO 參考，不作為新功能開發位置。
- 使用 PostgreSQL `project_db` 的既有資料模型；不遷移 DEMO SQLite 的帳號、貼文、留言。
- 允許配合開發調整 PostgreSQL，結構變更前先備份，以 migration 管理；不因餐廳與評論另有原始檔就省略備份，其他應用資料仍須保護。
- 保留 DEMO 主要視覺與操作方式，先沿用原生 HTML／JavaScript 與 FastAPI，不以更換前端框架為第一階段目標。
- 會員使用模擬付款，不串接真實金流；畫面明示不會扣款。會員期間暫定 30 天。
- 推薦提供可替換的基礎實作，不宣稱已完成個人化演算法。
- GitHub 儲存庫：<https://github.com/sxiang0705/Foodiemo>。只保存程式碼、文件與安全的設定範例，不提交機密、資料庫快照或使用者上傳檔案。

## 2. 起始狀態

目前已透過 DBeaver 成功連上 PostgreSQL 9.5.25，並在 `project_db.public` 看到與盤點文件一致的 14 張表。完整欄位、限制與實際資料仍需由後端唯讀核對。

參考文件：[資料庫現況](../文件檔案/現況與目標文件/資料庫現況.md)。文件記錄有 158 間餐廳、30,420 筆評論，這些是先前盤點值，不作為後續測試的固定筆數斷言。

尚未完成：後端專用 Tunnel、應用程式連線、版本管理、測試資料庫、備份還原驗證與 v1 功能實作。DBeaver 連通不等於後端已連通。

## 3. 架構與目錄

資料流：瀏覽器 → FastAPI → PostgreSQL。照片檔案由獨立儲存層管理，資料庫保存照片位置、排序及關聯。

本機開發先採 Windows 執行後端，經獨立 SSH Tunnel 存取 Ubuntu 的 PostgreSQL。部署位置在後續部署階段確認。前端不得持有資料庫或 SSH 帳密，也不直接連 PostgreSQL。

建議結構（實作時建立）：

```text
v1開發/
├── frontend/                 # HTML、樣式、頁面及共用 API 模組
├── backend/
│   └── app/
│       ├── api/              # 路由、輸入輸出及身分驗證入口
│       ├── services/         # 帳號、紀錄、會員、推薦等業務邏輯
│       ├── repositories/     # 資料查詢與寫入
│       ├── models/           # PostgreSQL ORM 對應
│       ├── schemas/          # API 資料格式
│       └── core/            # 設定、連線及共用安全機制
├── migrations/              # 既有 Schema 基線與後續變更
├── tests/                   # 單元、整合及 API 測試
├── docs/                    # API 契約、環境與部署說明
├── scripts/                 # 啟動、唯讀檢查及測試入口
├── .env.example             # 只有變數名稱與假值
├── v1開發流程.md
└── v1測試流程.md
```

模組按功能需求逐步建立，避免為目錄分層而加入不必要的抽象。正式資料以後端為準；localStorage／IndexedDB 僅用於必要的偏好、草稿或快取，不能決定登入身分、資料所有權或會員資格。

## 4. 資料對應與待核對差異

| 功能 | PostgreSQL 來源 | 整合事項 |
| --- | --- | --- |
| 帳號與個人資料 | `users` | 對應 `user_id`、`user_name`、`birthday`；確認頭像、Email 驗證及 Google 登入所需結構 |
| 餐廳與營業時間 | `restaurant_rows`、`business_hours` | 正確處理含大寫字母的欄位、缺值與非連續 ID |
| 原始餐廳評論 | `reviews_rows` | 與平台留言分開；不可把 `created_at` 當原始評論時間，現有表沒有結構化評分 |
| 餐飲紀錄與日曆 | `records` | 所有權、公私狀態、餐廳關聯、文字、三項評分與時間 |
| 照片 | `photos` | 一篇紀錄多張照片，依 `sort_order` 排序；檔案操作與資料庫失敗補償 |
| 平台留言 | `platform_comments` | `is_deleted` 軟刪除與目標紀錄的可見性 |
| 收藏與標記 | `favorites`、`record_mentions` | 去重及有效使用者／餐廳關聯；標記不自動授予共同編輯權限 |
| 會員與模擬交易 | `memberships`、`payment_transactions` | 會員有效期、模擬交易識別及重送處理，不沿用 DEMO 的單筆會員關聯假設 |
| 推薦及互動 | `recommendation_runs`、`recommendation_items`、`user_restaurant_events` | 排名、演算法版本、事件語意與推薦來源追蹤 |

按讚、檢舉、共同編輯及動態通知目前沒有完整對應，不把 DEMO 的提示視為已完成。這些功能列為後續擴充；v1 未實作時隱藏或清楚標示，避免顯示假的成功結果。

## 5. 分階段開發與驗收

### 階段 0：版本、連線與資料保護

1. 檢查本機與遠端 Git 狀態，建立版本基線；設定忽略規則，再檢查實際待提交內容。
2. 建立後端環境變數與獨立 SSH Tunnel，帳密由使用者在本機輸入。
3. 以唯讀查詢核對資料庫名稱、版本、Schema、欄位、限制、索引及應用程式權限，不輸出密碼雜湊或個資。
4. 在任何結構變更前完成備份，於隔離資料庫驗證還原；確認工具與 PostgreSQL 9.5 的相容性。
5. 建立獨立測試資料庫與測試照片儲存位置。權限不足時先整理可執行 SQL 與所需權限，交由資料庫 Owner 處理，不嘗試在正式資料庫替代執行破壞性測試。

驗收：後端唯讀連線成功，備份可還原，測試環境與 `project_db` 隔離，機密未進入 Git。版本升級另行評估，不把環境升級與功能 migration 混在同一次變更。

### 階段 1：後端骨架、Schema 基線與餐廳查詢

1. 建立 FastAPI 設定、資料庫連線、錯誤回應及日誌入口，鎖定並驗證依賴版本。
2. 依既有 PostgreSQL 建立 ORM 與 migration 基線，既有資料庫先核對後標記基線；新測試資料庫需能重建結構。
3. 禁止把 DEMO 啟動時自動建表／補欄位流程直接套到 `project_db`；缺少資料庫設定時明確失敗，不退回 SQLite。
4. 建立餐廳列表、分頁／篩選及詳情 API，提供前端穩定的欄位格式。
5. 將探索頁接上真實餐廳；沒有照片、評分、價位或營業時間時呈現缺值，不補造資料。

驗收：瀏覽器可顯示真實餐廳，餐廳 ID 正確，空清單、缺值、API 失敗均有可辨識狀態；測試依 [v1測試流程](v1測試流程.md) 執行。

### 階段 2：帳號、登入與個人資料

1. 完成註冊、登入、登出、目前使用者查詢與登入過期處理。
2. 明確規劃密碼儲存、Email 驗證、密碼重設及頭像所需的 migration。
3. Google 登入需另外設定供應商資訊；尚未完成時不顯示可用的登入入口。
4. 前端統一處理未登入與登入失效；後端由驗證身分推導操作使用者，不信任請求提供的 email 或會員旗標。

驗收：帳號流程可用、錯誤不暴露敏感資料、跨帳號操作遭拒，登入失效不被顯示成「沒有紀錄」。外部郵件或 Google 設定未完成時，於驗收報告列出限制。

### 階段 3：收藏、餐飲紀錄、照片與日曆

1. 串接收藏新增／移除與清單。
2. 串接紀錄建立、查詢、編輯、刪除，允許選擇餐廳或只填地點，處理三項評分及公開狀態。
3. 完成照片上傳、排序、單張刪除與整篇刪除；驗證檔案格式及大小，避免部分失敗留下不一致資料。
4. 日期由明確時區規則決定，日曆預設以 Asia/Taipei 顯示。
5. 修正 DEMO 的取消離開仍跳轉、整篇刪除只刪首圖及空結果保留舊日曆等問題。

驗收：登入 → 選餐廳 → 建立附照片紀錄 → 日曆／個人頁查看 → 編輯／刪除，重新整理後資料仍一致。

### 階段 4：公開紀錄與留言

1. 社群探索讀取真實公開紀錄，個人清單讀取自己的紀錄。
2. 詳情、照片存取與留言 API 一起遵守公私及所有權規則；不可只在列表隱藏私人紀錄。
3. 留言使用安全文字渲染，依軟刪除狀態顯示。

驗收：公開紀錄可見，私人紀錄不能被其他帳號直接取得；留言可保存且不執行 HTML／腳本。

### 階段 5：推薦接入介面與互動紀錄

1. 與演算法團隊確認版本化契約，提供輸入輸出範例與可選欄位說明。
2. 建議輸入：由後端取得的使用者 ID、推薦數量、可選地點／分類條件；推薦模組不取得密碼或驗證憑證。
3. 建議輸出：餐廳 ID、排名、可選分數與原因；後端補齊餐廳資料並產生推薦執行 ID。
4. 初始提供依條件篩選、穩定排序的基礎推薦，標示其版本；未使用個人化資料時不宣稱個人化。
5. 保存 runs／items；定義曝光、點擊、收藏事件的觸發時機、去重方式、時間與推薦關聯。
6. 演算法實作須可獨立替換，先以介面隔離，不預設其一定同程序執行或一定使用特定模型套件。

驗收：基礎推薦能跑完整流程；以另一個測試推薦實作替換時，前端及公開 API 格式不需修改。新的資料需求或契約變更仍需版本協調，不能承諾任意演算法零修改接入。

### 階段 6：模擬付款與會員

1. 顯示「模擬付款，不會扣款」，不收集卡號、CVV 或真實付款資料。
2. 後端只對目前登入者開通，保存明確標示為模擬的交易與會員資料；交易識別不得與未來真實金流混淆。
3. 使用重送識別確保同一次付款重複送出不重複開通，交易與會員更新保持一致。
4. 預設一次開通 30 天；建議有效期間內不允許再次購買、不累加天數，到期後可重新開通，實作時同步介面文案。
5. 後端判斷會員有效期，前端 localStorage 修改不會改變權限。v1 不假裝提供尚未實作的會員功能。

驗收：付款前提示清楚，登入者可完成模擬交易並取得會員狀態，重送不重複生效，到期狀態正確。

### 階段 7：整合與交接

- 執行核心流程、權限、資料一致性及必要手機版面測試，記錄失敗、修正及重測結果。
- 提供 README、API／推薦契約、資料庫變更、啟動、備份還原及部署說明。
- 確認部署位置、HTTPS、Cookie／跨來源設定、照片存取、日誌與服務重啟方式。
- 推送前檢查機密與資料檔排除情況；不得以 force push 覆蓋未知遠端內容。

驗收：另一位組員能依文件啟動並執行測試；推薦團隊能根據契約接入；已完成、未完成與外部設定限制有清楚清單。

## 6. 每一階段共同完成條件

1. 程式已實作，資料庫變更有 migration 與回復策略。
2. 對應測試通過，必要瀏覽器操作已驗證，不只通過語法檢查。
3. 設定範例、API 契約及操作文件與程式一致。
4. 未實作項目不以假成功掩蓋；外部依賴阻礙有明確記錄。
5. 變更可在 Git 追蹤，沒有提交憑證或真實使用者資料。

## 7. 下一個實際工作批次

先完成階段 0 與階段 1：版本基線、後端連線、資料庫備份與隔離測試環境、Schema 核對、餐廳 API 與探索頁。第一批不擴張到付款、社群全部功能或演算法研發。
